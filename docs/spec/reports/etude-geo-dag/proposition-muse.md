# Étude indépendante — Transfert scraping PV et détection des signaux de radar-immobilier vers geo
Proposition Muse (architecte, effort maximal) — lecture seule, aucune exécution coûteuse. Périmètre : PV municipaux, signaux de densification, croisement avec évaluations foncières. Contraintes rappelées : 0 Python (Node/TS + binaires natifs uniquement), `make` uniquement avec `ENV=<env>` en dernier argument, aucune exigence inventée ; tout élément non vérifié dans les sources lues est marqué `unverified`.

## A. État actuel chiffré
### A.1 radar-immobilier — ce qui tourne (source : `git show origin/main:deploy/k8s/*`, `api/src/scripts/refresh-pv.ts`)
- CronJob `radar-refresh-pv` : 4 passages/jour (`0 5,11,17,23 * * *` UTC prod, décalé d'1 h en préprod), `concurrencyPolicy: Forbid`, `backoffLimit: 0`, `activeDeadlineSeconds: 19800` (5 h 30), base `suspend: true` activée par overlays. Un passage balaie les ~528 villes config-only, reprend au curseur durable S3 `refresh/018/sweep/cursor.json` écrit avant chaque ville, traite au plus 1 document/ville/passage, sans plafond quotidien (`REFRESH_SWEEP_MAX_SUBMISSIONS=0` par défaut) ; échecs répétés → `abandoned` après `REFRESH_MAX_DOCUMENT_FAILURES`.
- Prérequis bloquant : sans graphe canonique existant, la ville est `no-baseline` et n'est pas rescrapée. Première visite = amorçage du registre `refresh/018/<ville>/coverage.json` sans appel modèle ; ensuite seuls les nouveaux documents sont payés (décision owner 2026-09-20). Les PV déjà projetés en masse ne sont pas ré-extraits.
- Durées : seule mesure citée dans le manifeste = 2 h 41 pour une acquisition 528 villes sur `worker-live`, explicitement un proxy et non une mesure du CronJob ; la fourchette 2 à 5 h de la demande owner est cohérente avec ce proxy + `activeDeadlineSeconds` 5 h 30, mais la durée réelle d'un passage complet en préprod/prod reste `unverified`. Repères unitaires cités : 17 documents = 4,3 min en Gemini low (p50 15,3 s/doc) contre 42 min en Astra low (p50 147,8 s/doc) ; refus qualité ~15 % sous repli Gemini.
- Job ponctuel `radar-scrape` (`33-scrape-job.yaml`) : `worker-live`, fenêtre 183 j, chunks de 25 villes, 100 itérations max, deadline 2 h, dépôt CAS S3 `raw/<city>/pv/cas/<sha>.<ext>` + manifeste `runs/<source>/<runId>/manifest.jsonl`, HEAD-skip idempotent ; `LIVE_SCRAPE_EXPLOIT=1` ajoute parse `pdftotext` (poppler) → `ontology/<city>/project-state.json`. Aucun LLM, Postgres optionnel (feed PG si credentials présents).
- Watchdog `radar-refresh-pending-watchdog` : toutes les 5 min, supprime tout pod `radar-refresh-pv` Pending > 900 s (préconditions uid/resourceVersion). Origine : incident 2026-10-09, double attachement PVC RWO keyring, 2 pods bloqués 4 h 30.
- Détection des signaux (`api/src/services/exploitation/signals.ts`) : signaux dérivés uniquement de `DesignationEvent` canoniques validés et reconciliés, avec `evidenceRefs` S3 obligatoire (anti-invention) ; kinds : `ppcmoi`, `derogation`, `cptaq-dezonage`, `residential-rezoning`, `intention`, `precedent` ; kinds faibles (`intention`, `precedent`) plafonnés à surveillance + `needs_review`. UUID déterministe v5 par seed. Consommation : routes `graph-signals`, `scoped-signal-facets`, `mcp-signal-search`, scoring `packages/radar-scoring` (Steve30) en aval.
- Adaptateurs sources : `packages/radar-sources` (`SourceAdapter`, `RawDocument`, `municipalities.qc.json`, `geo-source-inventory`, dizaines de spikes sous `sources/_spikes/` dont rôles d'évaluation foncière MAMH). Ontologie : `radar/ontology/ontology-profile.yaml` v2.2, 9 types de nœuds, 25 relations, préfixes figés (`muni-`, `source-`, `bylaw-`, `zone-`, `event-`, `signal-`, `lot-`, `adresse-`, `constraint-`), champs `etape`/`etape_date`/`zone_ref`/`no_lot`/`reglement_number`. Extraction via `@sentropic/engram` + `@sentropic/llm-mesh-refresh` (`api/src/services/graph/refresh-mesh.ts`, `refresh-run.ts`, `refresh-coverage.ts`, `refresh-sweep.ts`).

### A.3 cluster-mesh et Engram — état vérifié
- `@sentropic/cluster-mesh` 0.1.0 (`/home/antoinefa/src/sentropic/packages/cluster-mesh`) : contrats fédéraux (membership, trust, device, tenant boundary, projections signées locales, cycle NHI h2a) avec runtime dégénéré mono-instance (`mode: single-node`). Découverte inter-serveurs, échange de jetons RFC 8693, résolution distante de projections, réplication mémoire : seams définis mais `CapabilityGatedError` (fail-closed). Aucun broker HTTP, aucune file de travail, aucun routeur LLM. Côté h2a, `cluster-mesh` désigne aussi le backend de remise d'enveloppes signées de `h2a_send` (présence + inbox) — transport de messages entre agents, pas un moteur de DAG.
- Engram = runtime graphe `@sentropic/engram` (dépôt `graphify`, pipeline `detect → extract → build → cluster → analyze → report → export`, nœuds/arêtes/hyperarêtes avec confiance `EXTRACTED|INFERRED|AMBIGUOUS`). radar l'utilise déjà comme moteur d'extraction/projection (client `TextJsonGenerationClient`, `mergeExtractions`, graphe canonique par ville → projection Postgres). Engram ne fait ni capture réseau, ni ordonnancement, ni file.
- LLM : chemin séparé et déjà tranché côté geo (`SPEC_PIPELINES_MIGRATION.md` §3) — `llm-mesh enroll`/gateway, pods sans credentials fournisseurs, `mistral-medium-*` vision banni (ADR-0024), seul `mistral-ocr-latest` sanctionné. Confondre cluster-mesh et routeur LLM serait une erreur d'architecture (désaccord sol/fable consigné dans la spec, non retranché ici).

### A.4 Points faibles (motivants le transfert)
1. Monolithe séquentiel radar : 1 CronJob, 1 doc/ville/passage, rotation bornée par la durée d'un passage (2 à 5 h) ; un arriéré multi-documents/ville met une journée à se vider.
2. Couplage graphe → scrape : `no-baseline` empêche l'acquisition des villes sans graphe canonique ; l'acquisition (coût dominant) est subordonnée à la projection.
3. Fragilité d'ordonnancement : watchdog Pending dédié, incident PVC RWO, `backoffLimit: 0` sans reprise intra-passage, logs pods expirant en 24 h (compensés par rapports S3).
4. Duplication radar/geo : deux jeux d'adaptateurs QC (`radar-sources` vs `qc-sources`), deux registres municipaux, deux chaînes PV (528 vs 1 106 villes) sans contrat partagé.
5. Croisement foncier faible : les rôles d'évaluation MAMH existent en spike radar et en lane geo (cadastre/rôle, `immo-lots`, `lotZoneJoin`) sans jointure systématique signal × lot × évaluation au même endroit.
6. Côté geo : capture encore partiellement locale, preuve v2 à 0/1 106, T5 (DAG) non construit, CronJob PV séquentiel lent, deux CronJobs backlog homonymes à images divergentes signalés par la spec de migration (`unverified` sur l'état courant exact).

## B. Architecture cible — DAG managé dans geo
Principe : geo devient le producteur unique capture → extraction → graphe → signaux ; radar devient consommateur pur (projection PG, scoring, API/MCP, UI). On étend la cible déjà spécifiée par geo, on ne la remplace pas.
- Template DAG `geo-refresh-lane-v1` (par lane) : `detect-change → plan-worklist → capture-to-S3-CAS → classify → native/structured → OCR si score insuffisant → LLM Engram si résidu admissible → validate/close-partition → materialize immutable release → readback gates → invalidate downstream joins → promote current pointer (atomique, coherence_id)`. Chaque nœud lit des artefacts S3 immuables et écrit un artefact versionné (`run_id` + hash des entrées) ; fraîcheur par hash, pas par cron aveugle. Le DAG décide, le LLM exécute : au plus les 3 nœuds LLM déjà identifiés par geo, gardés par `when:` sur score d'insuffisance, réponse cachée par `(input_sha, prompt_version, model_policy)`.
- Lane PV/signaux (priorité) : index PV → capture document → `pdftotext` → OCR si scan → parse Engram (profil ontologique v2.2 porté dans geo) → `DesignationEvent` canoniques → dérivation signaux (règles actuelles de `signals.ts` portées telles quelles) → événements `zone-change-candidate` par ville, qui déclenchent les lanes règlement/normes/zones concernées. Lanes cadastre/rôle (aucun LLM, voir risque Loi 25 §E) et `immo-lots` (`lotZoneJoin`/`enrichWithNorms`) rejoignent le même graphe : c'est ce qui rend le croisement signal × lot × évaluation foncière natif (même `coherence_id`, mêmes identifiants `lot-`/`zone-`/`signal-`).
- Moteur d'orchestration : Argo Workflows sur `poc-k8s` (reco convergence geo, à ratifier owner — §F) ; chaque nœud reste un Job k8s Node/TS autonome et réversible vers CronJob. Toute commande passe par `make <cible> ENV=<env>` avec `ENV` en dernier argument, dans geo comme dans radar.
- Rôle cluster-mesh (plan de contrôle, pas moteur de calcul) : identité de workload et frontière tenant par nœud (résolution `tid` par membership validé, jamais copiée d'un id de requête) ; distribution signée des demandes de travail et des receipts entre conducteur, lanes et consommateur radar (enveloppes h2a backend `cluster-mesh`, présence, inbox) ; attestation NHI des comptes de service des Jobs. cluster-mesh ne transporte ni octets PV ni appels LLM : les octets passent par S3, les appels LLM par `llm-mesh`/gateway.
- Rôle Engram (moteur sémantique) : extraction structurée des PV (profil ontologique partagé, versionné), construction/validation du graphe canonique par ville, annotation `DesignationEvent`/`Signal` avec citations (`docSha`, page) et confiance, `mergeExtractions` incrémental. Engram est invoqué par le nœud LLM du DAG avec octets déjà captés ; il n'initie aucun fetch.
- Contrat de données geo → radar : extension du contrat servi v1.0.0 existant, sans rupture. (1) Même mécanisme pointeur CAS + snapshot SHA-256, `schema_version` incrémentée en mineure additive. (2) Ajouts par ville : références CAS raw/parsed, graphe canonique versionné, signaux dérivés (kind, `etape`, `etape_date`, `zone_ref`, `no_lot`, `reglement_number`, `evidenceRefs[]`), événements `zone-change-candidate`, `coherence_id` commun avec zonage/normes/rôle pour le croisement foncier. (3) Géométries servies par l'API OGC existante ; aucun accès direct de radar à la DB geo, ni l'inverse.
- Ce que radar consomme : un snapshot vérifié (hash contrôlé avant usage), projeté dans son Postgres (tables `graph-signals`, facettes, recherche MCP inchangées), scoré par `radar-scoring` inchangé. radar conserve : API, UI, scoring, alertes, son CronJob en lecture seule pendant la coexistence (§D). radar abandonne à terme : `worker-live`, `refresh-pv`, adaptateurs `radar-sources` (dépréciés au profit de `qc-sources`), watchdog associé.

## C. Fonctions complémentaires à demander
### C.1 À cluster-mesh (dépôt `sentropic`, package `@sentropic/cluster-mesh` ; backend h2a)
- CM-1 File de travail durable multi-tenant : dépôt/revendication/ack de demandes signées (ville, lane, `input_sha`) avec lease et reprise, au-delà de l'inbox h2a actuelle. Justification : le DAG a besoin d'une distribution reprise-sur-curseur équivalente à `sweep/cursor.json`, mais multi-lanes et multi-consommateurs ; aujourd'hui absente (runtime mono-instance).
- CM-2 Résolution distante de projections signées (lever le gate `remote signed-projection resolution`). Justification : radar doit vérifier l'identité/producteur d'un snapshot geo sans confiance implicite de bucket.
- CM-3 Découverte inter-serveurs et révocation de membres (lever les gates discovery/revocation). Justification : `poc-k8s` + poste conducteur + éventuel second cluster doivent se voir et se révoquer ; sinon la distribution reste mono-nœud.
- CM-4 Échange de jetons RFC 8693 pour identité de workload éphémère par Job. Justification : les pods DAG ne doivent porter aucun secret fournisseur durable ; l'identité doit être celle du nœud/lane/tenant, révocable.
- CM-5 Journal d'attestation requêtable (qui a produit quel `run_id`, quand, sous quelle policy). Justification : traçabilité des receipts DAG et du gate de promotion `coherence_id`, aujourd'hui portée par des rapports S3 par dépôt.
- CM-6 Ne pas demander : routage LLM, transport d'octets, ordonnancement DAG. Justification : déjà couverts (gateway `llm-mesh`, S3, Argo) ; les ajouter à cluster-mesh créerait le cul-de-sac signalé par la passe fable de `SPEC_PIPELINES_MIGRATION.md`.
### C.2 À Engram (dépôt `graphify`, package `@sentropic/engram`)
- EN-1 Extraction incrémentale idempotente par document : entrée `(docSha, ontology_version, prompt_version, model_policy)` → sortie cachée/rejouable sans ré-appel modèle. Justification : le modèle de coût radar actuel (ne payer que le nouveau) doit survivre au transfert ; prérequis du cache DAG.
- EN-2 API d'annotation typée `DesignationEvent`/`Signal` (kinds, `etape`, `zone_ref`, `no_lot`, citations page) comme contrat stable et versionné, indépendant du format graphe complet. Justification : c'est l'unité consommée par radar et par l'événement `zone-change-candidate` ; aujourd'hui la dérivation vit côté radar (`signals.ts`).
- EN-3 Validation/close-partition en bibliothèque : partition fermée par ville (tout document = extrait, refus motivé, ou `unknown`), jamais de vert par omission. Justification : reprendre la règle geo « un refus est un état » et l'anti-invention radar (`evidenceRefs` obligatoire).
- EN-4 Liaison typée graphe ↔ référentiels geo : arêtes `signal → zone/lot/règlement` résolues contre les identifiants servis par geo (pas de chaînes libres). Justification : condition du croisement avec zonage et évaluations foncières ; la spec geo `SPEC_GRAPHIFY_TYPED_LINKING_CAPABILITY.md` va dans ce sens (`unverified` sur son état d'implémentation).
- EN-5 Mode batch headless DAG : exécution sans session d'assistant, bornée (timeout, taille doc, tentatives), receipts structurés par document. Justification : aujourd'hui l'orchestration par skill suppose un agent ; le nœud DAG exige un binaire déterministe.
- EN-6 Ontologie partagée gouvernée : profil unique versionné (ex v2.2 radar) hébergé côté geo, avec test de compatibilité consommateur. Justification : éviter la divergence de profils radar/geo pendant et après la migration.

## D. Migration par lots, sans interruption pour radar
Règle commune : radar ne change de source qu'après double lecture concordante ; tout lot est réversible par re-pointage du snapshot consommé et/ou re-pin du digest d'image (mécanisme déjà prévu par le contrat servi et par le lifecycle geo). Aucun lot ne supprime l'ancien chemin dans la même étape que l'armement du nouveau.
- Lot 0 — Convergence et hygiène (préalable) : aligner les checkouts sur `origin/main`, committer le CronJob geo actif non suivi, dédoublonner les CronJobs backlog, épingler les images par digest, installer Argo (poc-k8s), porter le profil ontologique v2.2 dans geo en dual-lecture. radar inchangé. Retour arrière : nul (aucun trafic déplacé).
- Lot 1 — Capture PV dans geo, radar en shadow : la lane PV geo capture les mêmes villes que `radar-refresh-pv` (périmètre 528 d'abord, puis 1 106) vers le CAS S3 geo sans publier vers radar ; comparaison automatique des manifests (documents vus/traités/écartés) avec les rapports `refresh/018/sweep/reports/<cycle_id>.json` radar sur plusieurs cycles. Retour arrière : arrêter la lane shadow ; radar poursuit seul.
- Lot 2 — Extraction et signaux en double production : Engram s'exécute dans le DAG geo ; les signaux geo sont projetés dans une base radar de préprod (ou schéma parallèle) et diffés contre la production (`make test-api ENV=test-*`, jamais `ENV=dev` ; comptages par ville/kind, taux de `needs_review`, écarts d'`evidenceRefs`). Le CronJob radar continue d'alimenter la prod. Retour arrière : radar reste sur sa projection ; les artefacts geo restent immuables et ignorés.
- Lot 3 — Bascule de consommation : radar pointe vers le snapshot geo vérifié (nouveau `snapshot_sha256`) pour la projection des signaux ; `radar-refresh-pv` passe en `suspend` mais reste déployé une fenêtre d'observation (au moins 4 cycles, soit 1 journée, cible recommandée 7 jours `unverified` — à fixer owner). Le scoring et l'API ne changent pas de contrat. Retour arrière : re-pointer `latest.json` consommé vers le dernier snapshot radar et désuspendre le CronJob (curseur S3 intact, reprise sans perte).
- Lot 4 — Croisement foncier et extinction : activation des jointures signal × lot × rôle d'évaluation dans le graphe geo (lane cadastre/rôle selon ADR Loi 25, §E) ; exposition à radar via le même snapshot enrichi ; puis suppression du chemin radar (`worker-live`, `refresh-pv`, watchdog, adaptateurs dépréciés) dans la PR qui constate la bascule, sur le modèle geo « le shard de la lane passe à 0 dans la même PR ». Retour arrière après suppression : restaurer la dernière image radar épinglée par digest et son CronJob depuis git (aucune donnée perdue, les CAS des deux côtés sont append-only).

## E. Risques, coût, effort par lot
Efforts en ordres de grandeur d'ingénierie (semaines-personnes), `unverified` faute de vélocité mesurée commune ; coûts d'infrastructure dominés par pods d'extraction et appels LLM, non chiffrés ici (`unverified` — dépend du placement gateway et des quotas, §F).
- Lot 0 : effort faible (jours). Risque : découvrir d'autres workloads actifs non committés. Coût : nul hors temps.
- Lot 1 : effort moyen (2 à 4 semaines `unverified`) — réutilise `pv-refresh-cron`/`pv-capture-backlog` existants. Risques : politesse/robots sur 1 106 sites municipaux, IP datacenter bloquée (déjà documenté côté geo, Obscura/Tor en dernier recours), double capture transitoire (coût réseau faible, dédupliquée par CAS).
- Lot 2 : effort principal (4 à 8 semaines `unverified`) — nœud Engram headless (EN-1/EN-5), parité des signaux. Risques : divergences d'extraction LLM (modèle/policy), coût LLM si le cache par hash n'est pas au rendez-vous, rappel : ne payer que le nouveau document, jamais de ré-extraction de masse. Garde : partition fermée, écart de parité bloquant la bascule.
- Lot 3 : effort faible (jours) mais risque de service le plus élevé. Risques : snapshot geo incomplet pris pour complet (mitigé par `complete:true` + vérif SHA-256 + gate de parité), latence de fraîcheur (rotation geo quotidienne vs 4 passages radar — voir §F), retour arrière exercé au moins une fois en préprod avant bascule.
- Lot 4 : effort moyen, étalable. Risque juridique dominant : Loi 25 sur le rôle foncier (champs personnels) — conformément à la reco geo, pas de migration cadastre/rôle sur cluster sans ADR dédiée ratifiée et allowlist fail-closed ; tant qu'elle manque, le croisement se limite aux champs d'emplacement non personnels et l'adresse précise reste `unknown`. Risque secondaire : suppression prématurée du repli radar ; mitigé par la fenêtre d'observation du Lot 3.
- Risques transverses : dépendance à un composant cluster (Argo) installé par poc-k8s ; gates cluster-mesh (CM-1 à CM-4) non livrées — le DAG doit fonctionner sans elles (identité k8s native + S3) et les adopter comme durcissement, jamais comme prérequis bloquant ; confusion cluster-mesh/routeur LLM (écartée §A.3/CM-6) ; dérive ontologique si EN-6 n'est pas tenu.
